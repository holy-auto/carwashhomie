# カードコレクション・ゲーミフィケーション 設計ドキュメント

> 施工事例・お役立ち情報の**滞在時間 / 回遊 / 再訪 / 来店**を伸ばすための、
> 「散らばったカードを集めてブックを完成させる」体験の設計書。
> HUNTER×HUNTER グリードアイランド編の「ブック」から着想。
> このドキュメントは**設計フェーズの成果物**であり、実装コードは含みません。

- ステータス: ドラフト（実装前レビュー用）
- 対象ブランチ: `claude/card-collection-gamification-4el3p3`
- カード設置先（初期）: **施工事例（gallery）** と **お役立ち情報（useful）**
- 前提スタック: Next.js App Router + Supabase + 既存の管理画面（`/admin`）
- **会員モデル: 「お試し先行 → LINEログイン会員登録」**（下記「会員・LINE連携」章）
  - 未登録でも数枚は拾える（離脱を防ぐフック）→ 保存・続き・特典受取のタイミングで
    **LINEログイン**（会員登録）に誘導。ログイン時に**公式アカウント友だち追加も同時に促す**。
  - 会員化＝友だち母数の増加 → 後から**一斉告知（ブロードキャスト）／セグメント配信**が可能。

## 1. 目的とKPI

### 狙い
1. **滞在時間の増加** — 記事や事例を"最後まで読む"動機（カードは本文中に潜む）。
2. **回遊の増加** — 別ページにも別のカードがある → サイト内を巡る。
3. **再訪の増加** — コンプ手前で止めておく設計 + 期間限定カード → また来る。
4. **来店/CVの増加** — マイルストーン報酬をクーポン/LINE特典に接続し、来店・予約へ橋渡し。
5. **友だち母数の増加** — カード保存の動機で**LINE会員登録＝公式アカウント友だち追加**を積み上げ、
   後から**一斉告知・セグメント配信**できる資産（母数）を育てる。

### 計測するKPI（Phase 3で本格計測、Phase 1でも簡易ログは残す）
| KPI | 取り方 |
| --- | --- |
| カード付き記事の平均滞在時間 | GA4 等の `engagement_time` を設置有無で比較 |
| カード取得率（記事到達→取得） | `card_collected` イベント / 記事PV |
| **会員化率（未登録→LINE登録）** | LINEログイン完了数 / カード取得ユーザー数 |
| **友だち追加率・友だち総数** | ログイン時の友だち追加成立数 / LINE公式アカウント管理画面の友だち数 |
| ブックページ到達率・コンプ率 | `/book` PV、コンプユーザー数 |
| クーポン発行→使用率 | 発行コード数 / 店頭・LINEでの消込数 |
| 再訪率 | 取得ユーザーの7日/30日以内再訪 |

## 2. 体験フロー（ユーザー視点）

```
施工事例 / お役立ち記事を閲覧
        │  本文中に「キラッと光るカード」が潜んでいる
        ▼
カードをタップ → 取得アニメ → 「◯◯を手に入れた！」トースト
        │  未登録でもOK（ゲスト取得はいったん端末=localStorageに保持）
        ▼
ヘッダー/フッターに「ブック ▐▐▐ 2/24」進捗バッジが増える
        │
        ▼   ★お試しの上限（例: ゲストは3枚まで/保存はできない）に触れると…
┌─────────────────────────────────────────────┐
│  「集めたカードを保存して続きを集めよう」        │
│  [ LINEではじめる ]  ← ワンタップ会員登録         │
│   └ LINEログイン（同時に公式アカウント友だち追加を促す）│
│      → ゲストのlocalStorage分をアカウントに引き継ぎ     │
└─────────────────────────────────────────────┘
        │  以後は端末をまたいでも自分のブックが表示される（会員）
        ▼
/book（ブック）を開く
   ├─ 取得済み: カード表面＋めくると「洗車お役立ち要約(Tip)」が読める
   ├─ 未取得 : シルエット＋「どのあたりにありそう」ヒント → 該当ページへ回遊
   └─ 進捗   : 「あと3枚でシルバー特典」など次の報酬を提示
        │
        ▼
マイルストーン到達 → LINEショップカードのQR/URL提示 → 店頭で付与 → 来店・予約
        │
        ▼
（運営）友だち母数に対して LINE公式アカウント管理画面から一斉告知（ブロードキャスト）
```

- **お試し先行**: 初見でも登録前に数枚拾えるので離脱が少ない。**保存したくなった瞬間**に
  LINE登録へ誘導するのでコンバージョンが高い（＝方針A）。
- 「集めたカードを後から開くと洗車お役立ち情報の要約が読める」= 各カードの `description`。
  **ゲーム目的で来た人にも実利（知識）と来店動機が残る**のが本施策の肝。
- ゲスト取得分は**登録時にアカウントへマージ**（`user_collections` へ移送）。二重・不正は
  サーバー側の unique 制約で吸収（後述）。

## 3. カードの世界観・仕様

### レアリティと入手難度（＝カウント重み）
**入手難度をレアリティに紐付け、コンプ/マイルストーン判定は「枚数」ではなく「ウェイト（重み）」で数える。**
簡単なカードは1枚のウェイトを小さく（＝複数枚で1カウント）、SSは単体で特典が出るほど重くする。

| ランク | 位置づけ | 入手難度 | カウント重み（例・要オーナー確認） |
| --- | --- | --- | --- |
| N（ノーマル） | 基本の洗車Tip | 易しい（記事を読めば拾える） | **複数枚で1カウント**（例: 0.5＝2枚で1） |
| R（レア） | 事例に紐づく施工ノウハウ | 普通 | 1枚＝1カウント |
| SR | 季節・キャンペーン限定 | やや難（期間限定） | 1枚＝2カウント相当 |
| SS（シークレット） | 隠し・イベント | 難（隠し要素） | **単体で特典**（`instant_reward`） |

> 重みの具体値・「何カウントで何の特典か」は **報酬ラインと一体でオーナーと要検討**（§12）。
> データ的には各カードに `count_weight`（重み）と `instant_reward`（SS等の単体特典フラグ）を持たせ、
> **数値を管理画面から後から調整**できるようにしておく（設計を固定しない）。

### 1枚のカードが持つ情報 ＆ ビジュアル（GI風カードをベースにする）
添付のグリードアイランド風カードの体裁を**ベース**にする（内容は洗車 homie 用に差し替え）。
カード表面のレイアウトは概ね次の3段構成：

```
┌─────────────────────────────┐
│  100  │   島の地図   │  G-400  │ ← 上段: 番号 / 名前 / コード
├─────────────────────────────┤
│         （イラスト画像）        │ ← 中段: ビジュアル
├─────────────────────────────┤
│  島の形だけが示されている地図…    │ ← 下段: 説明テキスト（キラ枠で囲む）
└─────────────────────────────┘
```

- **`card_number`**: 左上の大きな番号（例 `100` / `673` / `1217`）。通し番号・図鑑No.として使う
- **`name`**: 中央のカード名（例「島の地図」→ 洗車用の名称に差し替え）
- **`code`**: 右上のコード（例 `G-400` / `SS-1` / `F-150`）。**取得判定のキー**にも流用
- **`image_url`**: 中段イラスト（画像 or カラー。未設定でも `accent_color` で成立させる）
- **`description`（旧 `tip_summary`）**: 下段に**カード表面として表示**する説明＝「洗車お役立ち要約」。
  ブックで開いたときにも読める（実利が残る）
- **`hint`**: 未取得時にブックへ出す「ありそうな場所」ヒント（回遊誘導）
- **枠色（レアリティ表現）**: 添付同様、通常は**金のキラ枠**、SS・特別カードは**深紅/ピンクの枠**など、
  `rarity` で枠デザインを出し分ける
- 掲載元（どの記事/事例に紐づくか）＝取得地点

> カードの**キラッと光る質感**は CSS のシマー/ホログラム風エフェクトで表現する（世界観の遊び）。
> 版権配慮のため、**フォント/イラスト/文言はオリジナルにする**（GIは体裁の参考に留める）。

## 4. データモデル（Supabase）

既存テーブル（`gallery_cases`, `useful_articles` など）と同じ流儀で追加する。
**公開列は RLS で anon 読み取り可**、書き込みは service-role（管理API）のみ。

### 4.1 `collectible_cards` — カードマスタ（管理画面で編集）
| 列 | 型 | 説明 |
| --- | --- | --- |
| `id` | uuid pk | |
| `code` | text unique | 右上コード（例 `G-400` / `SS-1`）。**取得判定のキー** |
| `card_number` | int null | 左上の大きな番号（図鑑No.。例 `100`/`673`/`1217`） |
| `name` | text | カード名（中央） |
| `rarity` | text | `N` / `R` / `SR` / `SS`（枠色・出し分けに使用） |
| `category` | text null | 分類（例: 洗車, コーティング, 内装…） |
| `description` | text null | 下段の説明テキスト＝ブックで読める「洗車お役立ち要約」 |
| `hint` | text null | 未取得時のヒント |
| `image_url` | text null | 中段イラスト。未設定なら色で描画 |
| `accent_color` | text null | 画像なし時の背景色 |
| `count_weight` | numeric default 1 | **コンプ/マイルストーンでの重み**（易しいカードは <1、例 0.5） |
| `instant_reward` | bool default false | **単体で特典が出る**か（SS等）。true なら取得即特典対象 |
| `series` | text null | セット名（季節/キャンペーン等。コンプ判定単位に使える） |
| `sort_order` | int | 並び順 |
| `published` | bool | 公開/非公開 |
| `created_at` | timestamptz default now() | |

> マイルストーン判定は「取得カードの `count_weight` 合計」で行い、`instant_reward` のカードは
> 取得時点で個別に特典対象にする。**重みや閾値はデータ側で調整可能**にしておく（§3）。

### 4.2 カードの「設置」— 既存コンテンツへの紐付け
既存の `gallery_cases` / `useful_articles` に**設置用の列を1つ足す**方式を基本とする
（新テーブルを増やさず、管理画面の1フィールド追加で済む）。

- `gallery_cases.card_code` text null … その事例に潜ませるカードの `code`
- `useful_articles.card_code` text null … その記事に潜ませるカードの `code`

> 1記事に複数枚潜ませたくなったら、後で中間テーブル
> `content_card_placements(content_type, content_id, card_code, position)` に拡張可能。
> 初期は1コンテンツ=最大1枚のシンプル運用で開始する。

### 4.3 進捗の保存（ゲスト＝端末／会員＝サーバーの二層）

方針Aでは**未登録（ゲスト）でも遊べ、登録すると引き継がれる**ので、保存先を二層に分ける。

- **ゲスト（未登録）**: **ブラウザの localStorage** に取得済み `code` の配列を保持。
  - 例: `chw:collection = { codes: ["WASH-01","CASE-03"], updatedAt: ... }`
  - **お試し上限**（例: ゲストは3枚まで、または保存不可）を設け、超過時にLINE登録へ誘導。
  - 割り切り: 端末をまたげない・Cookie消去でリセット。**ゲストのままでは報酬原資を乗せない**。
- **会員（LINEログイン後）**: 下記 `user_collections` を**正**とする。ログイン直後に
  localStorage のゲスト分を**サーバーへマージ**（unique 制約で重複吸収）→ 以後は端末非依存。

会員登録＝LINEログインは **Phase 1 から中核**（方針A）。詳細は「会員・LINE連携」章を参照。

#### `members` — 会員（LINEユーザー）
| 列 | 説明 |
| --- | --- |
| `id` uuid pk | |
| `line_user_id` text unique | LINEログインで得た本人ID（`sub`） |
| `display_name` text null | LINEプロフィール名（任意・同意範囲で） |
| `is_friend` bool | 公式アカウント友だちか（配信対象判定に使用） |
| `created_at` timestamptz default now() | 登録日時 |

#### `user_collections` — 会員の取得カード
| 列 | 説明 |
| --- | --- |
| `id` uuid pk | |
| `line_user_id` text | 会員ID（`members.line_user_id`） |
| `card_code` text | 取得カード |
| `collected_at` timestamptz | 取得日時（不正検知・分析用） |
| unique(`line_user_id`,`card_code`) | 二重取得防止 |

> `members` と `user_collections` は **RLS で anon 直アクセス不可**にし、
> 書き込みは**LINEトークンを検証したサーバー（API Route / service-role）経由のみ**にする
> （ゲスト用の公開カードマスタ読み取りとは分離）。

## 5. 管理画面への組み込み

既存の**ホワイトリスト方式**（`lib/admin-resources.ts` の `RESOURCES`）にリソースを1つ追加するだけで、
`/admin` の汎用エディタ（`components/admin/ResourceEditor.tsx`）にそのまま乗る。

```
cards: {
  table: "collectible_cards",
  fields: ["code","card_number","name","rarity","category","description","hint",
           "image_url","accent_color","count_weight","instant_reward",
           "series","sort_order","published"],
  numericFields: ["card_number","count_weight","sort_order"],
  booleanFields: ["instant_reward","published"],
  order: { column: "sort_order", ascending: true },
  label: "コレクションカード",
}
```

加えて、既存の `gallery` / `useful` リソースの `fields` に `card_code` を足せば、
**「この事例/記事にどのカードを潜ませるか」を管理画面から選べる**ようになる。

`lib/content.ts` には `getCards()`（公開カード一覧）を、既存 fetcher と同じ
`getPublicClient()` → 失敗時デフォルトのパターンで追加する。

## 6. フロントエンド構成

### 6.1 カードを潜ませる `<CardDrop code="WASH-01" />`
- 施工事例ページ（`app/gallery/page.tsx` → `components/BeforeAfter.tsx` 付近）と
  お役立ち記事（`components/Useful.tsx`）の本文レンダリング内に差し込む。
- 表示: 小さめの光るカード。ホバー/タップで取得。
- クリック時: localStorage に `code` を追記 → トースト表示 → 進捗バッジ更新。
- 取得済みなら「取得済み」表示に切り替え（再取得しない）。

### 6.2 進捗バッジ（グローバル）
- `Navbar.tsx` か固定フッターに `ブック n/N` を常時表示 → `/book` への導線。
- クライアント状態は軽量な React Context（`CollectionProvider`）で共有。

### 6.3 ブックページ `/book`
- グリッドのバインダー風UI（添付のブック見開きイメージに寄せる）。
- 取得済み: 表面＋タップで**裏返って `description`**（洗車お役立ち要約）を表示。
- 未取得: シルエット＋`hint` → 「探しに行く」ボタンで該当カテゴリのページへ。
- 上部に進捗ゲージと「次の報酬まであと◯枚」。
- シリーズ別タブ（季節/キャンペーン）でコンプ単位を提示。

### 6.4 状態管理・SSRの扱い
- 既存の公開ページは `export const dynamic = "force-dynamic"` のServer Component。
- カードマスタ（`getCards()`）は**サーバー取得**、取得済み状態は**クライアント（localStorage）**。
  → ハイドレーション後に「取得済み/未取得」を反映（サーバーは未取得前提で描画してチラつき回避）。

## 7. 会員・LINE連携（お試し先行モデル ＝ 方針A）

「HPで会員登録（LINE連携）→ 自分のカードが表示される」を**LINEログイン**で実現する。
会員登録の副産物として**公式アカウントの友だち母数**が積み上がり、後から**一斉告知・
セグメント配信**ができる。ここが本施策の集客・再訪エンジン。

### 7.1 会員登録＝LINEログインの仕組み
- ユーザーが「**LINEではじめる**」をタップ → LINE認証 → こちらは**LINEユーザーID（`sub`）**を
  受け取る。これがそのまま**会員登録**になる（**別途パスワード不要**）。
- IDをキーに `user_collections` に集めたカードを保存 → **端末をまたいで自分のブックが表示**。
  現行のゲスト（localStorage）分は**ログイン直後にサーバーへマージ**して引き継ぐ。
- 取得できるプロフィールは同意範囲（表示名・アイコン程度）。**メール等は必須にしない**。

### 7.2 友だち追加を「同時に」促す（母数を増やす）
- LINEログインには**ログインと同時に公式アカウントの友だち追加を促すオプション**があり
  （`bot_prompt`）、`会員登録 = ログイン + 友だち追加` を**1フロー**にまとめられる。
- これで**登録が進むほど友だち母数が増える**。友だちであれば後述の配信対象になる。
- `members.is_friend` に友だち状態を持たせ、配信可否・分析に使う
  （友だち解除の Webhook を受ければ最新化できる）。

### 7.3 一斉告知（ブロードキャスト）— ショップカード止まりの方針
- **一斉告知（ブロードキャスト）**: 友だち全員へ新カード・キャンペーン・来店促進を配信。
  → これは **LINE公式アカウント管理画面（LINE Official Account Manager）から手動でOK**。
  **こちらでプログラム（Messaging API）を組む必要はない**ので、まずはこれで十分。
- **特典（報酬）連携は「LINEショップカード」止まり**にする（オーナー方針）。
  自動クーポン配信（Messaging API push）は**今回作らない**。付与は**ショップカードのQR/URL誘導＋店頭**で行う。
- **将来オプション（今回はやらない）**: `user_collections` を使えば「5枚以上だけ」等の
  **セグメント配信（ナローキャスト）**も可能だが、それは Messaging API 実装が要るため後日検討。

### 7.4 料金・上限（正直な現実）
| 項目 | 実態 |
| --- | --- |
| LINEログイン設定 | LINE Developers で **Loginチャネル**を作成（**無料**） |
| 友だちを増やす | **友だち追加そのものは無料**。母数はいくら増えても課金されない |
| 配信（ブロードキャスト/プッシュ） | **Messaging API**。**配信通数に月次の無料枠と上限**があり、超過分は
  有料プラン（無料枠＝コミュニケーションプランは月数百通規模、超えるとライト/スタンダード）。
  **母数×配信回数**で通数が増えるため、告知頻度は無料枠と相談 |
| データ保存 | LINEユーザーIDを保存 → **プライバシーポリシー**に利用目的を明記（既存 `/privacy` に追記） |

> ブロードキャストは友だち数×回数だけ通数を消費する。母数が大きくなったら
> **全員配信を乱発せず、セグメント配信で通数を節約**するのがコスト最適。

### 7.5 実装の要点（技術）
- **チャネル構成**: LINE公式アカウント（既存）＋ 同一プロバイダーに **Loginチャネル**（会員登録用）。
  ショップカード止まりの方針なので、**今回は Messaging API のプログラム実装は不要**
  （告知は管理画面、特典はショップカードで回す）。
- **サーバー検証**: フロントで取得した LINE のトークンを **Next.js の API Route** で検証し、
  正当な `line_user_id` を確定してから `members` / `user_collections` に書き込む
  （クライアントから直接 DB に書かせない）。
- **環境変数**（`.env` / デプロイ先のシークレット。**コミットしない**）:
  `LINE_LOGIN_CHANNEL_ID` / `LINE_LOGIN_CHANNEL_SECRET` など（Loginチャネル分）。
- **友だち状態 `is_friend`**: ログイン時の同時友だち追加で概ね把握できる。厳密な追跡（解除検知）は
  Messaging API の Webhook が要るため、**今回は必須にしない**（将来オプション）。
- **LIFF（任意の簡略化）**: 公式LINEのトーク画面から開く導線なら **LIFF** でログインボタンを
  省け、プロフィールを自動取得できる。Webサイト単体なら通常のLINEログインでよい（両対応可）。
- **同意・規約**: 保存する情報と利用目的（カード保存・告知）を登録前に提示。
  LINE公式アカウントガイドライン／景品表示法の観点は §9 とあわせて明記。

## 8. 報酬設計（ここが事業リスクの分水嶺）

「HP上で集めたカード → LINEスタンプが自動で溜まる」の**スタンプ自動付与は公式には無い**。
オーナー方針により**特典連携は「LINEショップカード」止まり**とし、**Messaging APIの自動配信は作らない**。
（＝方針A：ゲストで遊び始め、保存・特典受取のタイミングで会員化する）

> **報酬ラインそのもの（割引率・条件・期限・何カウントで何を出すか）は、
> 入手難度のウェイト設計とあわせて別途オーナーと要検討**（§3・§12）。以下は仕組みの枠だけ。

### カウントの数え方（入手難度ウェイト）
- マイルストーンは**枚数ではなく `count_weight` の合計**で判定（易しいカードは複数枚で1カウント）。
- `instant_reward` のカード（SS等）は**取得した時点で単体の特典対象**にする。

### ゲスト段階（未登録）
- 数枚は拾えるが、**報酬原資は乗せない**（localStorage はなりすまし可能なため）。
- お試し上限に触れたら「**保存して特典を受け取るにはLINE登録**」へ誘導。

### 会員段階（LINEログイン後・Phase 1 から稼働）
- コレクションは `user_collections` に保存され、**サーバーが `line_user_id` で重複付与を検証**。
- マイルストーン到達／`instant_reward` 取得で、画面に **LINEショップカードのQR/URLを提示** →
  **付与は店頭スタッフがショップカードで実施**（デジタルの自動配信は行わない）。
- 段階特典の中身（例のような割引・来店特典）は**オーナーと詰めてから**設定する。

### 告知への接続
- 会員＝友だちなので、新カード追加・季節キャンペーンを **LINE公式アカウント管理画面から一斉告知**
  （ブロードキャスト）して**再訪・来店**に繋げる（§7.3）。

> 景品表示法・LINE公式アカウントガイドラインの観点で、特典条件（上限・期限・除外）は
> 事前に明記する。高額景品を"確率"で配る設計は避け、**達成型（コンプ=確定特典）**にする。

## 9. 不正対策・エッジケース

| 論点 | ゲスト（未登録）の扱い | 会員（LINEログイン）の扱い |
| --- | --- | --- |
| Cookie消去で集め直し | 許容（報酬は乗せない） | LINE本人紐付けで実質無効化 |
| 同一カード二重取得 | localStorageで重複排除 | DBの unique(`line_user_id`,`card_code`) |
| ゲスト→会員のマージ時の重複 | — | サーバーで upsert、unique 制約で吸収 |
| 非公開/削除カードの取得済み表示 | 表示時に公開マスタと突合し無効分は隠す | 同左 |
| 報酬の濫用 | 報酬を出さない（登録へ誘導） | サーバー検証＋ショップカードは店頭付与で最終判断 |
| SSRとの不整合（チラつき） | 初期は未取得で描画→ハイドレーション後に反映 | 同左 |
| 友だち解除後の配信 | — | `is_friend` を Webhook で更新し配信対象から除外 |

## 12. 未決事項 / 決定事項

### 決定済み（このレビューで確定）
- **設置密度**: **1記事1枚が基本**（人気記事の複数枚化は将来オプション）。
- **カードのビジュアル**: **添付のGI風カードを体裁のベース**にする（番号／名前／コード＋イラスト＋
  下段の説明＋キラ枠）。内容は洗車homie用に差し替え、**文言・絵・フォントはオリジナル**にする。
- **入手難度**: レアリティに難度を紐付け、**易しいカードは複数枚で1カウント（`count_weight`）**、
  **SSは単体で特典（`instant_reward`）**。判定は枚数でなくウェイト合計。
- **LINE連携の深さ**: **ショップカード止まり**。会員登録（LINEログイン）＋友だち追加＋
  管理画面からの一斉告知までで、**Messaging APIの自動クーポン配信は作らない**。

### 引き続き要検討（オーナーと）
- **報酬ライン**: 何カウントで何の特典か、割引率・条件・期限、SS単体特典の中身。
  → `count_weight` の具体値・マイルストーン閾値と**一体で決める**（データ側で後から調整可能）。
- **初期カード総数**とシリーズ構成（季節/キャンペーンの走らせ方）。
